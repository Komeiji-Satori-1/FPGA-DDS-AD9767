# Codex 协作准则与项目提示词

本文档用于约束 Codex 在 `fpga-dac-awg` 项目中的协作方式。适用项目路径：

```text
D:\individual_program\FPGA\project\fpga-dac-awg
```

## 一、核心协作原则

1. **工作区边界**
   - 所有任务默认只在项目工作区内执行。
   - 严禁脱离工作区读取、修改、生成或移动文件，除非用户明确授权。
   - 如必须访问外部参考工程、芯片资料或示例代码，只能先说明目的、范围和风险，再等待授权。

2. **先沟通，后实现**
   - 任何新功能开始实现前，Codex 必须先分别以“产品经理”和“架构师”视角与用户沟通。
   - 产品经理视角负责澄清需求、使用场景、优先级、验收标准和功能边界。
   - 架构师视角负责拆分模块、说明调用关系、接口定义、时序风险、复用方案和测试策略。
   - 未经用户确认，不得直接进入新功能代码实现。

3. **代码改动前的远程仓库要求**
   - 每一次代码修改前，必须先检查 Git 状态和远程仓库状态。
   - 在修改代码前，必须确保当前工作已提交并推送到远程仓库。
   - 如果没有远程仓库、远程不可用、存在未提交代码、或无法确认当前代码已推送，必须停止代码修改并询问用户。

4. **新建代码文件的分支要求**
   - 每次新建代码文件前，必须新建并切换到独立分支。
   - 分支命名建议使用：

```text
feature/<功能名>
fix/<问题名>
experiment/<实验名>
```

   - 仅新增或修改 Markdown、CSV、TXT 等说明性文本文件时，无需切换新分支，除非用户另有要求。

5. **代码改动留痕**
   - 所有代码修改都必须在 `DOC` 目录中留下记录。
   - 建议维护以下文件：

```text
DOC/change_log.md
DOC/design_decisions.md
DOC/register_map.md
DOC/architecture.md
```

   - 每条记录至少包含：
     - 日期
     - 分支名
     - 修改文件
     - 修改原因
     - 影响范围
     - 验证方式
     - 未解决问题

6. **最小改动原则**
   - 不要随意修改已有函数名称、模块名称、端口名称、变量名称和文件名称。
   - 即使存在无用代码，也应优先保留，除非用户明确要求清理。
   - 只修改与当前任务直接相关的部分。
   - 如果必须重命名或删除，应先说明原因、影响范围和替代方案，并等待用户确认。

7. **复用优先**
   - 优先复用项目内已有代码、外部授权示例工程、已有引脚约束和已有文档。
   - 对于参考工程中的代码，必须先说明哪些文件可以直接复用，哪些需要改造，哪些不建议复用。
   - 对自动生成的 IP 文件，例如 PLL、ROM、Quartus Megafunction，应谨慎复用。若 Quartus 版本差异较大，优先建议重新生成 IP。

8. **验证要求**
   - 每次代码修改后，应说明已执行或建议执行的验证方式。
   - 对 FPGA 工程，验证可包括：
     - 语法检查
     - 仿真 testbench
     - Quartus Analysis & Synthesis
     - Pin Planner 检查
     - 时序报告检查
     - 板级测试步骤

## 二、代码修改前标准流程

Codex 在修改 Verilog、SystemVerilog、Python 脚本、Quartus 工程文件或其他代码文件前，必须执行以下流程：

1. 检查当前目录是否为项目工作区。
2. 检查 Git 当前分支。
3. 检查是否有未提交改动。
4. 检查是否配置远程仓库。
5. 确认当前代码已提交并推送到远程仓库。
6. 如果需要新建代码文件，则先新建功能分支。
7. 向用户说明即将修改的文件、目的和预期影响。
8. 用户确认后再修改代码。
9. 修改完成后，在 `DOC` 中记录变更。
10. 执行可行的验证，并向用户报告结果。

## 三、新功能启动前标准提问

任何新功能进入实现前，Codex 必须至少澄清以下问题。

### 产品经理视角

- 这个功能解决什么具体问题？
- 用户如何操作这个功能？
- 第一版必须具备哪些能力？
- 哪些能力可以放到第二版？
- 验收标准是什么？
- 是否需要兼容已有工程或已有接口？

### 架构师视角

- 需要新增哪些模块或文件？
- 可以复用哪些已有模块？
- 模块之间的调用关系是什么？
- 时钟域如何划分？
- 复位策略是什么？
- 配置寄存器如何设计？
- SPI、按键、DDS、DAC 输出之间如何协作？
- 需要哪些 testbench 或板级测试？
- 哪些地方存在时序、跨时钟域或资源风险？

## 四、适用于本项目的功能描述建议

本项目建议描述为：

```text
双通道 AD9767 DDS 任意波形发生器 FPGA 核心
```

推荐功能边界：

1. 双通道独立 DDS 输出。
2. 支持正弦波、方波、三角波。
3. 支持离线生成 ROM 波表和 `.mif` 文件。
4. 支持按键本地调频。
5. 支持 MCU 通过 SPI 配置：
   - 通道选择
   - 波形选择
   - 频率控制字
   - 初相位
   - 输出使能
6. 支持 DDS 相位累加和查表输出。
7. 支持 AD9767 双通道并行数据输出接口。
